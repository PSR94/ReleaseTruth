# v0.1.0 release checklist

ReleaseTruth should be tagged/published only from a commit that satisfies every gate below. The source tree contains the automation for these checks; GitHub Actions is the authoritative result for the commit being released.

## Product

- deterministic `behavior.lock` v1 capture/fingerprint/compare path is present
- all six adapters produce real observations in the TruthShop demo
- flagship API, browser, accessibility, CLI, event and performance regressions are asserted by E2E
- text, JSON, Markdown, JUnit, SARIF and HTML reports are generated and validated
- baseline/history/blame/bisect local provenance commands are implemented
- API persistence and dashboard history/comparison pages are part of E2E

## Quality gates

```bash
cargo fmt --all -- --check
cargo clippy --locked --workspace --all-targets --all-features -- -D warnings
cargo test --locked --workspace
pnpm install --frozen-lockfile
pnpm check:ts
ruff check apps/api
pytest -q apps/api
docker compose build
pnpm --filter @releasetruth/browser-adapter exec playwright install chromium
./scripts/e2e.sh
```

Or run the canonical wrapper:

```bash
make release-check
```

## Persistence and security

- PostgreSQL `alembic upgrade head` succeeds from an empty database
- SQLite local startup remains zero-setup
- webhook ingestion is disabled by default
- enabled production webhook mode requires a secret and rejects missing/invalid signatures
- duplicate webhook delivery IDs are idempotent
- `.env.example`, self-hosting guide and trust model reflect actual configuration

## CI/release automation

The `CI` workflow must show green jobs for:

- Rust checks
- TypeScript and Next.js checks
- FastAPI checks + PostgreSQL migration smoke
- Container build smoke
- Composite Action smoke
- Behavioral capture to dashboard E2E

The E2E artifact must contain behavior locks, all report formats, logs and dashboard screenshots.

The tag workflow must re-run validation before packaging Linux/macOS/Windows CLI archives and generating SHA-256 checksums.

## Documentation

Before publishing, confirm the root README, changelog, roadmap, API guide, architecture guide, GitHub Actions guide, self-hosting guide, security/trust model and CLI guide all describe the tagged code rather than planned functionality.

## Publishing rule

Never create or move a release tag to bypass a failed gate. Fix the source, obtain a fully green validation run on `main`, then tag that exact commit.
